# Datenbank-Architekturentscheidungen – Querschnittsleitfaden M3-L1–M3-L6

## 1. Nicht nach Produkten, sondern nach Problemen entscheiden {#S1}

Die Begriffe *Replikation*, *Partitionierung*, *Sharding*, *Serializable* und *Point-in-Time Recovery* beschreiben **verschiedene Anforderungen**. Sie sind keine austauschbaren Stufen einer unvermeidlichen Cloud-Karriere.

Wer eine kleine Datenbank betreibt, muss zunächst die Frage beantworten: *Was funktioniert noch nicht zuverlässig oder ausreichend schnell?* Eine komplizierte Antwort auf das falsche Problem erhöht die Betriebskosten, ohne den eigentlichen Mangel zu beheben.

**Erste Faustregel:** Nicht vom vermeintlich größten System ausgehen und rückwärts vereinfachen. Bei einfachen Anforderungen ist eine einzige vernünftig betreute Datenbank oft die technisch bessere Entscheidung.

## 2. Vier Schutzfunktionen, vier verschiedene Versprechen {#S2}

Bei einer Datenbank muss man unterscheiden, **welche Frage** beantwortet werden soll:

1.  **Transaktion:** Wird eine zusammengehörige Änderung logisch korrekt abgeschlossen? Etwa: Reservieren und Bestand reduzieren gelten zusammen.
2.  **Replikation und Hochverfügbarkeit:** Gibt es einen weiteren Knoten, der bei Ausfall übernehmen kann, und ist der Umschaltvorgang abgesichert?
3.  **Sharding:** Kann ein großer Datenbestand oder die verteilbare Last auf mehrere eigenständig zuständige Datenbereiche verteilt werden?
4.  **Backup und Wiederherstellung:** Kann ein früherer, unabhängiger und möglichst fehlerfreier Zustand wiederhergestellt werden?

Das zweite ersetzt das vierte nicht. Eine versehentliche Löschung kann innerhalb von Sekunden auf sämtliche Replikate übernommen werden. Ebenso macht Sharding eine Anwendung nicht automatisch schneller: Eine Abfrage über *alle* Shards kann sogar teurer werden. Und eine Datenbank mit ACID-Transaktionen ist ohne unabhängige Sicherung weiterhin gegen bestimmte Schäden ungeschützt.

``` text
                       Anwendung
                           |
                      Transaktionen   <- fachliche Korrektheit
                           |
                  Datenbank / Primärsystem
                         /    \
             Replikation    Verteilung     <- Verfügbarkeit / Last
                         \    /
                     Datenbestand
                           |
                unabhängige Sicherungen  <- Wiederherstellung
```

Die Skizze bedeutet nicht, dass jede Ebene tatsächlich benötigt oder in genau dieser Anordnung implementiert werden muss. Ein kleines System kann mehrere dieser Anforderungen mit einem einzigen Prozess und getrennten Backups erfüllen.

## 3. Drei nachvollziehbare Entwicklungspfade {#S3}

### Pfad A – Privater Medienkatalog

Ein lokales Programm verwaltet 150.000 Videos und Bilddateien mit Tags und Notizen. Die bloße Anzahl der Einträge erzwingt keine verteilte Datenbank. **SQLite mit sinnvoller Indizierung** kann die Arbeit sehr gut leisten. Die wesentliche Verlustgefahr betrifft die selbst erfassten Notizen und Zuordnungen. Deshalb ist eine konsistente und unabhängig aufbewahrte Sicherung wertvoller als eine vermeintlich hochmoderne Mehrknotenarchitektur.

Ein Beispiel: Jemand kopiert bei laufender SQLite-Datenbank nur die Hauptdatei, während zusätzlich Journal- oder WAL-Dateien verwendet werden. Das muss nicht den gewünschten vollständigen Zustand ergeben. SQLite bietet dafür eine **Online Backup API** und `VACUUM INTO`; eine Sicherung sollte außerdem testweise geöffnet werden. Die Medien selbst sind eine separate Sicherungsfrage.

### Pfad B – Kleiner öffentlicher Online-Dienst

Eine Webanwendung verwaltet Kunden, Berichte und Analyseaufträge. Eine einzelne PostgreSQL-Instanz genügt anfangs. Wird die Suche langsam, beginnt die Untersuchung bei Abfragen, Indizes, Cache und Engpassmessung. Erst wenn sehr viele **Lese**anfragen den Server begrenzen, kann ein Lese-Replikat helfen. Es muss aber nicht den unmittelbar neuesten Datensatz zurückgeben.

Wird die Anwendung geschäftskritisch, kann ein Standby die Unterbrechungszeit nach einem Hardwarefehler verringern. Die **Failover-Regel** muss jedoch definieren, welcher Knoten schreiben darf. Die bloße Existenz einer synchronen Kopie ist noch keine vollständige Sicherungs- oder Umschaltstrategie. Unabhängige Sicherungen und Restore-Proben bleiben notwendig.

### Pfad C – Sehr großer Dienst mit stark verteilbarer Schreiblast {#pfad-c-sehr-grosser-dienst-mit-stark-verteilbarer-schreiblast}

Erst wenn Messungen belegen, dass eine sinnvolle lokale Optimierung oder die Kapazität eines einzelnen Datenbankknotens nicht mehr ausreicht, wird ein Shard Key interessant. Beispielsweise können Daten verschiedener Kunden auf getrennten Shards liegen. Idealerweise bleiben die meisten Geschäftsoperationen eines Kunden innerhalb desselben Datenbereichs.

Problematisch wird ein Guthabentransfer **zwischen** zwei Kunden auf verschiedenen Shards: Eine erfolgreiche Abbuchung auf Shard A macht die Gutschrift auf Shard B noch nicht atomar. Verteilte Transaktionen oder fachlich geeignete mehrstufige Prozesse sind dann gesondert zu begründen. `Sharding` sagt allein noch nichts über die tatsächlich garantierte Transaktionskonsistenz.

**Zusatzgrenze:** Eine hashbasierte Verteilung verteilt fortlaufende Kennungen häufig gleichmäßiger, zerstreut aber Bereichsanfragen. Ein besonders aktiver Kunde kann selbst bei einem guten Hashschlüssel ein Last-Hotspot bleiben.

## 4. Drei Fehlerszenarien nicht verwechseln {#S4}

### A. Bestätigung ist verloren – wurde die Bestellung angelegt? {#a-bestätigung-ist-verloren-wurde-die-bestellung-angelegt}

Der Browser sendet einen Auftrag. Die Datenbank bestätigt erfolgreich, doch die Antwort erreicht den Browser nicht. Ein erneut gesendeter Auftrag kann eine Doppelbuchung erzeugen. Eine **Idempotenzkennung** macht es möglich, dieselbe beabsichtigte Operation wiederzuerkennen. Das ist ein Problem der Anwendungssemantik, nicht der Anzahl von Datenbankknoten.

### B. Der Primärserver fällt aus – welche Daten darf das Replikat bestätigen? {#b-der-primärserver-fällt-aus-welche-daten-darf-das-replikat-bestätigen}

Bei asynchroner Replikation können zuletzt bestätigte Änderungen auf dem Standby fehlen. Bei synchroner Replikation hängt die Garantie davon ab, **welcher Standby was bestätigt** und ob der richtige Knoten zum neuen Primärserver ernannt wird. Der alte Primärserver darf nicht später unerkannt erneut schreiben: Split-Brain muss verhindert werden. Ein Standby ohne gesicherte Rollenentscheidung ist keine vollwertige Hochverfügbarkeitslösung.

### C. Eine fehlerhafte Löschung wurde überall repliziert – welche Kopie hilft noch? {#c-eine-fehlerhafte-löschung-wurde-überall-repliziert-welche-kopie-hilft-noch}

Wenn der Fehler auf sämtlichen Replikaten angekommen ist, hilft die schnelle Replikation nicht. Nun kommt es auf den letzten **vor dem Fehler wiederherstellbaren** Sicherungsstand an. PostgreSQL kann bei passender physischer Sicherung und einer lückenlosen archivierten WAL-Folge eine **Point-in-Time Recovery** ermöglichen. Ein gewöhnlicher `pg_dump` ist jedoch keine Basis für WAL-Wiedergabe. Auch andere Komponenten wie Objektablagen, Schlüssel und Dateiverweise müssen zum rekonstruierten Zustand passen.

## 5. Zwei Zahlenspiele: Ziel ist nicht dasselbe wie Garantie {#S5}

**Ziel A:** Ein Dienst definiert ein RPO von fünf Minuten. Ein einziges Backup täglich um 02:00 Uhr erfüllt dieses Ziel bei einem Ausfall um 17:00 Uhr normalerweise nicht. Der Abstand beträgt in diesem konstruierten Beispiel **15 Stunden**. Er kann auch mit einem weiteren Server ungelöst bleiben, etwa wenn alle Kopien dieselbe Fehlbedienung übernehmen.

**Ziel B:** Ein Dienst definiert ein RTO von 30 Minuten. Die vorhandene Sicherung enthält zwar sämtliche wichtigen Daten, benötigt aber für Einspielen, Konfiguration und Anwendungsprüfung zwei Stunden. Dann wurde das RPO möglicherweise eingehalten, das **RTO aber nicht**. Messbare Wiederherstellungsproben liefern hier aussagekräftigere Erkenntnisse als ein ungetestetes Betriebsversprechen.

Die Werte sind **konstruierte didaktische Zahlen**, keine Benchmark-Ergebnisse oder allgemeinen Branchenziele.

## 6. Brücke zur Master-Vertiefung {#S6}

Der Kernbereich C liefert die Technik. Die abgeschlossenen Master-Kernlektionen zeigen, wie man dazu belastbare Aussagen trifft:

- **[M7-L2 – Korrektheit und Berechenbarkeit](M7-L2.md):** Eine fachliche Invariante wie „kein doppelter Verkauf“ muss ausdrücklich definiert werden. Ob ein Verfahren sie wahrt, ist eine Korrektheitsfrage.
- **[M7-L3 – Verteilte Systeme](M7-L3.md):** Ausfälle, Netzpartitionen, Konsens und fehlende globale Zeit erklären, weshalb ein erfolgreicher lokaler Zustand keine globale Garantie beweist.
- **[M7-L4 – Sicherheits- und Architekturentscheidungen](M7-L4.md):** Schutzbedarf, Risiko, Berechtigungen und Betriebsaufwand begrenzen die angemessene Architektur.
- **[M7-L6 – Forschungsmethoden und Synthese](M7-L6.md):** Eine Architekturentscheidung ist erst dann überzeugend, wenn Kriterien, Annahmen, Gegenbeispiele und Messgrenzen dokumentiert sind.

**Zusammenfassung:** Datenbanken werden nicht dadurch besser, dass sie möglichst viele verteilte Funktionen besitzen. Die passende Architektur erfüllt überprüfbare Anforderungen mit möglichst wenig unnötigem Koordinierungs- und Betriebsaufwand.
